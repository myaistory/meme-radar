# 补全吞吐设计

## 问题

原始发射事件的速度可能远高于GMGN、DEX和安全API的可用预算。若首次检查和多轮复查共享同一预算，旧复查会挤占新候选，高优先任务也可能在分析前过期。

## 预算隔离

当前调度将GMGN规模预算拆为：

- 三分之二用于首次规模检查；
- 三分之一用于规模复查；
- BSC、Base和Robinhood各有首次检查保留份额；
- DEX复查另有上限，不能占满全部DEX预算；
- 安全补全和Telegram仍使用独立预算。

所有主进程GMGN调用经过同一个串行节流器，调用间隔至少3秒。任何GMGN路径触发429或认证冷却时，发现和分析预算同步冷却，避免两个循环互相制造流量。

## 压力准入

队列未拥堵时保留正常覆盖。pending达到压力阈值后：

- 优先级60以上始终准入；
- 中优先候选需要GMGN成长、叙事爆发或跨链证据；
- 低优先事件只保留原始证据，不消耗补全API。

同一规则版本、链和CA只保留一个活动任务。更高优先事件可以替换旧pending任务，旧任务以 `TOKEN_COALESCED` 结束并保留审计记录。

## 分级规模复查

- 市值和持有人都低于20K/20：首次结果后结束；
- 两者都低于60K/60：只在10和20分钟复查；
- 更接近硬门：保留5、10、20、30分钟复查；
- 市值必须严格大于100K且持有人严格大于100，才进入后续DEX与安全分析。

这些规则只控制API预算，不降低任何安全或推送门槛。

## 验收指标

- 新高优先任务过期数为0；
- 到期pending稳定低于10；
- GMGN不持续429；
- 首次与复查预算可在health中分别观察；
- Telegram outbox无积压。
